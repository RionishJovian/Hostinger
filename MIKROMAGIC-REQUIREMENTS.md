> **Authoritative product requirements — updated 2026-10-07.** Build against the confirmed rules below. Future decisions should be added incrementally instead of blocking implementation.
## Product architecture
- **MikroTik = local gateway + HotSpot authentication/enforcement engine.**
- **MikroMagic = cloud control plane + synchronization + monitoring + multi-site coordination.**
- Guest internet traffic stays local: client → AP → MikroTik → SME ISP → Internet.
- MikroMagic management traffic uses a secure management path; WireGuard is the preferred direction for MikroTik management.
- Existing locally synchronized vouchers and local enforcement must continue if MikroMagic is temporarily unreachable.
- New multi-site voucher logins that require global concurrency coordination **fail closed** while cloud coordination is unavailable.
- Use two-way synchronization and reconciliation. If cloud and device state conflict, flag the conflict and ask the Owner/Admin which version to keep.
## Default site topology & commercial limits
- Default site: **1 MikroTik gateway → 1 managed switch → up to 5 managed APs → clients**.
- One site is included by default; additional sites are paid.
- MikroTik gateway management is charged separately; additional gateways at a site are paid.
- A second gateway at the same site is treated as a **separate network with its own voucher pool**, not a gateway group.
- Each MikroTik network has an SME-customizable display name.
- Default AP allowance is **5 per individual site**; extra AP capacity is paid.
- Third-party managed APs and switches are supported through vendor integrations where capabilities exist.
## Voucher profiles & lifecycle
- SME creates voucher profiles with validity, download quota, upload quota, download speed, upload speed, max simultaneous devices, applicable scope, and later HotSpot rules.
- Default max simultaneous devices = **1**, configurable upward with warnings about code-sharing risk.
- Validity starts on **first successful login**, not voucher creation.
- Validity is wall-clock from first activation; disconnecting does not pause it.
- Expiry is a hard cutoff and must be enforceable locally by MikroTik even if MikroMagic is offline.
- Download and upload quotas are independent hard limits. Either direction reaching its limit ends access.
- Download/upload quota may each be Unlimited.
- Validity may be Unlimited.
- Download/upload speed may each be Unlimited.
- Otherwise fixed fair-share speed = configured voucher bandwidth ÷ configured maximum devices. Unused capacity is not borrowed.
- Warn when effective download or upload is below 1 Mbps/device; exactly 1 Mbps does not warn.
- MikroTik should maintain accurate time with NTP.
## Multi-site vouchers & concurrency
- A voucher may be scoped to multiple shops/sites.
- First activation establishes one global activation/expiry timeline; synchronize absolute expiry.
- Simultaneous-device limits are combined globally across eligible shops when online.
- Existing sessions continue during MikroMagic outage; new logins requiring global coordination are blocked until coordination returns.
- A voucher limits **simultaneous active devices**, not permanent MAC binding.
- Release a device slot when the prior session is confirmed ended, with a short reconnect grace/detection period; exact timing remains implementation/RouterOS-validation dependent.
## Voucher states & actions
- Unused voucher may be deleted; deletion synchronizes to relevant MikroTiks.
- Once activated, Delete is unavailable; Disable is used while still valid.
- Disable immediately disconnects active sessions and blocks future login when reachable; if a router is offline, the pending disable is high priority on reconnect.
- Re-enable preserves original activation, usage, and expiry history.
- No Reset Voucher action.
- Expired vouchers are never reset/reused; create a new voucher.
- Expired and revoked vouchers remain in permanent voucher history.
- **Revoked** is permanent and cannot be re-enabled.
- Revocation occurs when Block Client is used on a voucher-authenticated client: block that device, disconnect it, revoke the associated voucher, and disconnect all other devices using that voucher across the SME.
## Voucher codes, bulk creation & printing
- VIP profile may use fully custom codes.
- Normal profiles allow SME-selected prefix + secure random **6-character** suffix.
- Generated suffix uses uppercase letters + numbers while avoiding confusing characters such as O/0 and I/1.
- Codes are case-insensitive and normalized internally to uppercase; generated codes must be unique within the SME voucher system.
- Bulk generation is supported.
- Printable voucher sheets are supported.
- Voucher code is always shown. Default printed SSID is optional in Shop Settings. QR is optional.
- QR scan opens captive portal and pre-fills voucher code; scanning alone does not activate the voucher.
## AP / Wi-Fi management
- Third-party AP targets include MikroTik, UniFi, TP-Link Omada, Ruijie/Reyee; additional vendors can follow.
- Generic/unsupported APs may still work in bridge/AP mode behind MikroTik but may require manual management.
- APs should normally operate bridged, with MikroTik remaining the gateway.
- Multiple SSIDs may feed the same MikroTik HotSpot/voucher pool.
- Basic managed settings: SSID, Wi-Fi security/password, Open network option, status, and connected-client information where supported.
- Guest Portal may suggest Open Wi-Fi but SME may retain WPA2/WPA3.
- AP Groups may apply common settings across multiple APs, including mixed brands.
- Partial bulk-update failures do not roll back successful APs.
- Offline AP changes become Pending and apply the **latest desired configuration** on reconnect.
- If local/vendor configuration changed while disconnected, flag a conflict and ask which version to keep.
- AP configuration conflicts are dashboard notices.
- Show AP source in client details.
## Managed switches
- Support third-party managed switches such as MikroTik, UniFi, Omada, Ruijie/Reyee where integrations allow.
- Do **not** expose remote PoE power-cycle control.
- Show which switch port each AP is connected to.
- Show port Connected/Disconnected status and link speed.
- Warn on dashboard if an AP expected at 1 Gbps negotiates only 100 Mbps.
## Device identity & presentation
- Gateway, switch, and AP can have customizable friendly name and location/note.
- Automatically detect brand/model where reliable.
- If exact model is known, show the actual product image for that model.
- If model is unknown, show a MikroMagic-themed icon appropriate to Gateway/Switch/AP.
- Automatically replace fallback icon with exact product image when model becomes known.
- Detect/display installed firmware/software version when supported.
## Client dashboard & controls
- Main dashboard shows total connected clients.
- Client details include device identifier, source AP/vendor, SSID, voucher code/profile, usage, remaining validity, status, MAC, and local IP where available.
- Disconnect Client ends only that device's current session.
- Block Client is SME-wide and permanent until manual Unblock.
- Blocked Clients page includes device/MAC, block time, source shop, optional reason, status, and Unblock.
- Unblocked voucher-based client needs a new voucher; old revoked voucher is not restored.
- Random/private MAC addressing means device identity/blocking is useful but not foolproof.
## Trusted Devices
- SME-wide Trusted Devices list.
- Trusted devices bypass captive portal and require no voucher.
- Unlimited by default from MikroMagic: no MikroMagic validity, quota, or speed cap; underlying network limits may still apply.
- Existing voucher session is not altered when a currently connected guest is added to Trusted; Trusted bypass begins on a later connection.
- Optional friendly name.
- Trusted connection history includes friendly name, MAC/IP, shop, AP/SSID, connect/disconnect times, and usage.
- Blocking a Trusted/no-voucher client blocks only the device; no voucher action.
## Monitoring, outages & notifications
- Gateway, managed switch, and individual AP outages use a **5-minute continuous-offline threshold**.
- After threshold: dashboard alert + push notification.
- Recovery sends a push notification.
- Use root-cause suppression: if gateway failure makes switch/APs unreachable, send one root-cause notification, not a flood.
- Recovery for a related outage is also one notification.
- Outage history stores root cause, affected devices, start, recovery, and duration for **1 month** and can be exported CSV/Excel.
- Show **30-day uptime percentage per individual device only**; no site-level uptime score.
## Firmware management
- Detect newer firmware where reliable.
- Owner/Admin may start firmware update from MikroMagic where vendor/device supports it; otherwise show update information only.
- Always show service interruption/restart confirmation first.
- Support scheduled firmware updates.
- Scheduled update runs at the chosen time even if clients are connected.
- Send push notification for both success and failure.
- Firmware update history is **view-only for 1 week**.
- Automatically create and verify a configuration backup before firmware update; if backup fails, do not start update.
## Backups & restore
- Automatic backups before firmware update, before restore, and before selected high-risk MikroTik HotSpot/network operations.
- Backup Now is available anytime; prevent overlapping backup operations.
- Backups are internal to MikroMagic: no SME download and no manual deletion.
- Retention = **7 days**, maximum **3 backups per device**.
- When a 4th backup is created, delete the oldest (FIFO); 7-day expiry also applies.
- Before restoring an older backup, create/verify a fresh safety backup. If safety backup fails, stop.
- Safety backups use the same 7-day / max-3 rules.
- Owner/Admin can restore from retained backups when supported.
- Renaming/location metadata, AP SSID/security/password changes, DNS changes, and LAN IP/subnet/DHCP range changes do not automatically trigger backup under the current product rules.
## Risky configuration changes, rollback & conflicts
- Show a strong confirmation warning before any change that may disconnect management or customers.
- After a disruptive change, show Applying → Waiting for gateway → Reconnected/Failed.
- If gateway remains unreachable after 5 minutes, automatically attempt rollback where a safe device-side/integration mechanism supports it.
- Successful rollback sends a push explaining the change failed and was restored.
- Rollback failure sends a critical push and marks **Recovery Required**.
- When manually recovered, detect reconnection, verify, reconcile state, clear Recovery Required, and send one recovery push.
- After recovery compare actual router configuration with MikroMagic expected state.
- Conflict shows **⚠ Configuration Conflict** and side-by-side differences.
- Owner/Admin chooses one whole version: **Keep Router Version** or **Keep MikroMagic Version**; no per-setting merge UI.
- While unresolved, router continues operating and safe operations such as voucher sync/client monitoring continue when possible.
- Keep MikroMagic Version: create safety backup first, then apply/verify.
- Keep Router Version: accept router state as new expected state; no backup required.
- Conflict resolution is logged. Configuration-conflict history is **view-only for 1 week**, no export.
## Logs & retention
- Single **Logs & History** area combines voucher history, guest sessions, trusted sessions, blocked clients, AP changes, router changes, outages, and relevant operational history.
- Owner/Admin only.
- Voucher history: permanent.
- Blocked-client history: permanent.
- Normal guest detailed session history: 3 months.
- Trusted-device detailed connection history: 3 months.
- AP configuration-change history: 3 months.
- MikroTik/router configuration-change logs: 1 month.
- Owner/Admin login history: 1 week.
- Configuration-conflict history: 1 week, view-only.
- Firmware update history: 1 week, view-only.
- Outage history: 1 month, exportable.
- For automatically deleted records, show **Retained until \[date\]** where applicable.
- Filter/export supported where previously specified; conflict and firmware history are not exportable.
## SME account & security
- One role only for SME: **Owner/Admin**.
- One Owner/Admin account per SME; multiple simultaneous signed-in devices are allowed.
- No public self-registration.
- MikroMagic operator manually creates/approves SME account and manually assigns a fixed username.
- Username cannot be changed by SME.
- Temporary credential is issued; first login forces SME to choose its own password.
- Minimum password length = **6 characters**; any characters are allowed, with no mandatory letter/number/symbol composition.
- Password strength indicator may warn without blocking a valid 6+ character password.
- SME may change password from Settings using current password; other sessions remain signed in.
- No self-service forgot-password recovery in v1. SME contacts MikroMagic operator; operator verifies and initiates reset; SME must choose a new password on next login.
- Password reset does not automatically log out existing sessions.
- Operator must never be able to view old/final passwords; use strong password hashing.
- Signed-in Devices page shows device/browser, login time, last active, current session; Owner/Admin can log out one selected session.
- Login history includes success/failure, time, device/browser, approximate source/IP, never password content.
- **5 failed attempts → 5-minute temporary lock → automatic unlock and counter reset.**
- Password-only authentication for v1; architecture may remain ready for future 2FA.

### Confirmed v1 architecture — Magic Hub and Magic Connect (Notion, 2026-10-09)
